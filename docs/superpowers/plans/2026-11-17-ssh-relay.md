# SSH relay Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or
> superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `op-reason.exe --ssh-agent`, a resident relay in front of the 1Password SSH agent that asks once per call
(per-call) or shows the facts next to 1Password's prompt (show-only), and `op-reason-ssh`, which carries a WSL call's
facts to it.

**Architecture:** Everything that is not Win32 lives in the core (`op_reason_core::ssh`: the agent protocol, Windows
command lines and masking, the roots of calls, `OPREASON_SSH_CALL`, the decision book and the queue, the SSH records)
and in the exe's portable modules (options, window texts), so that Linux tests cover it. The Windows part of the exe
serves a named pipe with one thread per client connection; the thread whose turn it is takes `Local\op-reason`, shows
the window (the existing Direct2D window, with buttons added) and passes the request on. The WSL binary chooses
`op-reason-ssh` by `argv[0]`, collects the call on `/proc` and `exec`s `ssh.exe`.

**Tech Stack:** Rust 2024 (two workspaces: the main one and `crates/op-reason-win`), the `windows` crate 0.62.2
(new features only, no new crates), bash tests, PowerShell for the screenshot script, GitHub Actions.

**Spec:** `docs/superpowers/specs/2026-11-17-ssh-relay-design.md`

**Execution:** inline (superpowers:executing-plans), one implementer: the tasks share types across both workspaces
and the Windows-only code can only be run by CI, so one person keeps the interfaces in step; a review of the whole
branch at the end.

## Global Constraints

- Default pipe `\\.\pipe\op-reason-ssh-agent`, upstream `\\.\pipe\openssh-ssh-agent`, mode `per-call`, time limit 60
  minutes from the decision, window answer wait 60 seconds (§3, §5.4).
- Messages: a 32-bit length, at most 256 KiB; longer closes the connection. Only sign requests are held; the relay
  never changes a message it passes on (§8).
- Pipe: `FILE_FLAG_FIRST_PIPE_INSTANCE`, a DACL for the current user only, `PIPE_REJECT_REMOTE_CLIENTS`, unlimited
  instances; one relay per logon session (§8).
- Decisions in memory only; forgotten when the root ends (Windows roots), after the time limit, or when the relay exits;
  a window without an answer fails that request and is not remembered (§5.4).
- Records: `%LOCALAPPDATA%\op-reason\ssh-log.jsonl`, own rotation and lock; never the data to sign or the signature;
  reason ≤ 500 characters, client command line ≤ 1000; command lines masked with the rules of `op` calls, the remote
  command kept (§9).
- `OPREASON_SSH_CALL`: ASCII JSON, bounded; `op-reason-ssh` never makes an ssh call fail, leaves the arguments and
  the standard streams alone (§7).
- No new crates; no version bump; `op-reason.exe` is built and run by CI only; nothing touches 1Password here.
- Texts in English and Japanese; the window never takes the focus and only a press and release on a button answers.

## Review Focus

1. A client that goes away while its request waits (Ctrl+C on `ssh` or ansible): its window closes when no request of
   the same call waits with it, nothing is remembered, and a queued request of a gone client never opens a window.
2. Agent messages split over several reads, a zero length, exactly 256 KiB and one byte more, a key list with many
   keys: the framing reads exactly one message and closes the connection only above the limit.
3. A client the relay cannot inspect (elevated, already exited, environment unreadable): the request still asks, as a
   call of its own, with "unknown" facts; it never passes silently and never panics the relay.
4. 1Password not running, its pipe busy, or 1Password closing the connection in the middle of a request: the client
   gets `SSH_AGENT_FAILURE`, the record says `no-upstream` or `failed`, other connections go on.
5. Japanese, control characters and very long values in `OPREASON_SSH_REASON` and command lines: normalized, clipped
   and masked in the window, the record and `OPREASON_SSH_CALL` (which stays ASCII and within its bound).

## Added after the checks of C1 and C4 (2026-11-18, spec §8 and §15)

- The relay watches its parent process: missing at start, or ended later, it shows a toast and writes a `ssh-relay`
  record (`what`: `no-parent`, `parent-ended`) (Task 6; texts in Task 5; the record in Task 3).
- A request that 1Password closes without an answer is recorded as `no-answer`; its toast says that a relay without a
  parent gets no answers when the parent is gone (Tasks 3, 5, 6).
- A forwarded connection shows both host keys: the outer `session-bind` (forwarding set: the remote host) and the inner
  one (the remote client's destination) (Tasks 5, 6).
- A connection that closes without a message leaves no record and no window (Task 6; the upstream is connected only
  on the first message).

### Task 1: Core — SHA-256 and the agent protocol

**Files:** Create `crates/op-reason-core/src/sha256.rs`, `crates/op-reason-core/src/ssh/mod.rs`,
`crates/op-reason-core/src/ssh/wire.rs`; modify `crates/op-reason-core/src/lib.rs`.

**Interfaces — Produces:**
- `sha256::digest(data: &[u8]) -> [u8; 32]`
- `ssh::wire::{MAX_MESSAGE (= 256 * 1024), FAILURE, SUCCESS, REQUEST_IDENTITIES, IDENTITIES_ANSWER, SIGN_REQUEST,
  SIGN_RESPONSE, EXTENSION, EXTENSION_FAILURE, SESSION_BIND}`
- `read_message(r: &mut impl Read) -> io::Result<Option<Vec<u8>>>` (the body; `None` at EOF before a header;
  `InvalidData` for a zero length or above `MAX_MESSAGE`), `frame(body: &[u8]) -> Vec<u8>`, `failure() -> Vec<u8>`
  (framed)
- `sign_request(body) -> Option<SignRequest { key, data, flags }>`, `session_bind(body) -> Option<SessionBind {
  host_key, forwarding }>`, `identities(body) -> Option<Vec<(Vec<u8>, String)>>`
- `purpose(data) -> Purpose { UserAuth { user }, Sshsig { namespace }, Other }`, `fingerprint(blob) -> String`
  (`SHA256:` + base64 without padding), `key_type(blob) -> Option<String>`

- [ ] Tests first: the FIPS 180-4 vectors (`""`, `"abc"`, the 448-bit message, a million `a`); byte vectors for a
  sign request, `session-bind@openssh.com` with and without forwarding, a key list of three keys; `read_message` over a
  reader that returns one byte at a time, a zero length, 256 KiB (accepted) and 256 KiB + 1 (rejected); the user name
  of a userauth request (`publickey` and `publickey-hostbound-v00@openssh.com`) and the namespace of an SSHSIG blob;
  the fingerprint of a known ed25519 key (`ssh-keygen -lf` value).
- [ ] Implement; `cargo test -p op-reason-core` passes.
- [ ] Commit.

### Task 6: The exe — the relay

**Interfaces — Consumes:** Tasks 1–3 and 5. **Produces:** `win::relay::run(args: &[OsString]) -> i32` (from `app::run`

- [ ] `pipe.rs`: server instances (SDDL `D:P(A;;GA;;;<user SID>)`), accept, client PID, `PeekNamedPipe`, the upstream

  (`ProcessCommandLineInformation`), the client's environment and directory from its PEB (x64 offsets, sizes bounded),

- [ ] `conn.rs`: one thread per connection; the upstream connected on the first message; `session-bind` and key-list

  second gets the window without buttons; records.
- [ ] `ask.rs`: the turn (a `Mutex` around `Book`, `Queue`, the key comments, the toast flag, with a `Condvar`); the
  turn's thread takes `Local\op-reason` (`OPREASON_LOCK_WAIT`) and writes `holder.json`, shows the window and the toast,

  no follower; after Allow the window says 1Password is asking until the reply.
- [ ] `mod.rs`: options, `--status`, `Local\op-reason-ssh-relay` (one per session), the first instance, `FreeConsole`
  when the console is the relay's alone, `ssh-relay` records, the accept loop, a sweep every minute, Ctrl+C. Clippy for
  the Windows target; commit.
