# Settings Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or
> superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** a settings layer with read, make-so and compare for every setting (§4 of the spec), the command line
`op-reason --settings …` on it, op-reason's scheduled task for the SSH relay, the skill placed for agents (Windows,
chosen folders, WSL distributions), and then a settings window, a Start menu entry and the relay's notification area
icon.

**Architecture:** `op_reason_core::settings` holds the list, the values, `settings.json`, the task's definition and
shape, the skill's mark and places, the WSL script, the decisions (an engine over a `System` trait), the command line's
parsing, texts and JSON, and the `settings` record; Linux tests run it against a fake `System`. `op-reason-win`
implements `System` (Task Scheduler's COM API, the relay's pipe and named objects, `wsl.exe`) and runs the command line
and the window; the relay reads its values from `settings.json` and tells its own (`relay.json`, a stop event). The WSL
executable passes `--settings` on to `op-reason.exe`.

**Tech Stack:** Rust 2024 (two workspaces), the `windows` crate 0.62.2 (new features only, no new crates), bash tests,
PowerShell 5.1 for the entry, GitHub Actions.

**Spec:** `docs/superpowers/specs/2026-11-23-settings-design.md`

**Execution:** inline (superpowers:executing-plans), one implementer, a fresh review of each pull request's branch at
the end: the tasks share one trait and its types across both workspaces, and the Windows code compiles locally only with
`cargo clippy --target x86_64-pc-windows-msvc` and runs only on CI. Tasks 1–13 are the first pull request
(`feat/settings-layer`), tasks 14–18 the second (`feat/settings-window`, based on the first).

## Global Constraints

- Setting names: `lang`, `relay.mode`, `relay.time-limit`, `relay.answer-wait`, `relay.autostart`, `relay.running`,
  `skill.windows`, `skill.wsl.<distribution>`, `skill.folder.<folder>`; the second pull request adds `relay.tray-icon`
  and `start-menu` (spec §4).
- Defaults: `lang` `default`, `relay.mode` `per-call`, `relay.time-limit` `60m`, `relay.answer-wait` `60s`,
  `relay.tray-icon` `on`, the rest `off`.
- `settings.json` stays `"v":1`; new fields `relay.mode`, `relay.timeLimit` (seconds), `relay.answerWait` (seconds),
  `relay.trayIcon` (boolean), `skill.folders` (list); other fields kept; writers hold `Local\op-reason-settings` (§6).
- Exit codes: `check` 0 same / 1 different / 2 usage or unreadable; `set` and actions 0 done / 1 not all done / 2 usage;
  `list`, `get` 0 / 2 (§7.3). WSL forwarding: 127 when `op-reason.exe` cannot be started.
- op-reason's task: `\op-reason-ssh-relay-<SID>` in the root folder; action `<exe> --ssh-agent`; triggers: logon of the
  user, and a time trigger from registration repeating `PT1M` without end; `InteractiveToken`, `LeastPrivilege`,
  `PT0S`, `IgnoreNew`, batteries allowed and not stopped, hidden, priority 5, no restart (§9.1).
- Stop and restart hold `Local\op-reason` (wait ≤ 2 s); the relay ends through `Local\op-reason-ssh-relay-stop-<pid>`,
  then `TerminateProcess` after 5 s; a start waits ≤ 15 s for the pipe (§9.2–§9.4).
- `--ssh-agent --status` output and exit codes, and the relay's options, unchanged; options win over the file (§8.1).
- Skill mark line, verbatim: `<!-- placed by op-reason <version>: op-reason --settings replaces this file when
  op-reason is updated, and removes it when the skill is turned off -->`, inserted after the front matter (§10.1).
- WSL script call: `wsl.exe -d <distribution> --exec sh -c <script> op-reason-skill <look|place|remove> <version>`,
  file on stdin, output `op-reason-skill 1 <state> <version|-> <path>`; `WSL_UTF8=1`; `docker-desktop*` left out.
- Records: `log.jsonl` record `{"event":"settings","from":"cli|window|tray","caller":…,"changes":[{"name","from","to","result","why"?}]}`
  (§15).
- No personal values in files, commits or PRs (`<you>` in paths). Comments and documents in English; the window and
  messages in English and Japanese.

## Review Focus

1. **A relay that runs a window when `relay stop` or a mode change arrives** — the stop must be refused without
   touching the relay or the task (engine test with the lock refused; Windows test with the lock held by a helper
   process).
2. **A relay started by the dotfiles' task (or by hand) while op-reason's task exists** — `get`, `check` and `set` must
   name it and never stop it; `set relay.autostart on` must not report a failure when the other relay answers (engine
   tests; Windows test with a relay started outside the task).
3. **A skills folder that is a symbolic link or a junction** (home-manager's `~/.claude/skills`) — `on` and `off` must
   refuse without writing; reading through it is fine (core tests with symlinks; WSL script tests; Windows junction test).
4. **`settings.json` written by an older op-reason or by hand** (unknown fields, a broken file, a bad `relay.mode`) —
   the relay must start with defaults, writers must keep unknown fields (file tests; relay test with a bad value).
5. **`check` run where op-reason.exe is newer than the relay that runs** (a relay of 0.6.0 without `relay.json`) — the
   mode must not be reported different, and `set` must restart only op-reason's task's relay (engine tests).
